LLM Agentic Workflow Architecture Pipeline Harnesses Skills Context MCPs Memory Links Reference

Expanded group walkthrough

How an LLM development workflow is wired.

A practical architecture for working with LLM coding agents: OMP or Hermes runs the session, skills steer the agent, MCPs control context and tools, and memory keeps knowledge available across sessions.

Primary external source: Model Context Protocol introduction. Handout: Agentic Stack Map.

Part 1 · Architecture

Four layers, four jobs.

The stack is understandable when each layer owns one responsibility.

Runtime

Harness

Owns: chat/session loop, permissions, model/tool calls, local working directory, subagents, UI.

Focus: OMP and Hermes.

Behavior

Skills

Owns: reusable procedures and behavioral constraints loaded when relevant.

Focus: Matt Pocock, caveman, Karpathy rules.

Context

MCP servers

Owns: external tools, resources, prompts, compression, retrieval, code graph access.

Focus: LeanCTX, RTK, Headroom, Codebase Memory, AgentMemory.

Persistence

Memory

Owns: long-lived structural and narrative context.

Boundary: generated memory helps recall; accepted truth belongs in durable docs.

Speaker note: Use this as the recurring frame. Every later tool answers one of these questions: Where does the session run? How should the agent behave? What outside capability does it need? What should survive?

Part 3 · Harnesses

Harness focus: OMP and Hermes.

OMP / Oh My Pi

FocusTerminal-firstLocal dev loop

What it is: the coding harness style for local terminal work. It brings the agent close to files, tests, shell commands, LSP/DAP, subagents, and hash-anchored edits.

What it owns: tool execution, edit safety, process state, local verification, and fast iteration.

Best fit: tasks where the agent needs to inspect code, make changes, run focused checks, and keep tight feedback with the repo.

Failure mode: if too many tools/context sources are enabled, the model may waste context choosing between them. Keep the tool surface intentional.

Official OMP site

Hermes

FocusAgent surfaceSkills + MCP

What it is: a Nous Research agent environment with MCP integration, skills, sessions, tools, memory configuration, and multiple interaction surfaces.

What it owns: agent profiles, skill invocation, MCP server management, sessions, and cross-surface workflows.

Best fit: workflows where the team wants skills and MCP management as first-class parts of the agent environment.

Failure mode: a harness can load skills and MCPs, but it does not replace them. Keep runtime, behavior, and capabilities separate in explanations.

Official Hermes docs

Alternatives: OpenCode, Codex CLI, Claude Code, Cursor, and other MCP-compatible clients can run similar patterns. They are intentionally secondary here.

Part 4 · Skills

Matt Pocock skills: implementation flow in order.

Use this as the actual implementation path. Do not jump straight to code when the idea still needs shaping.

1 · Shape

wayfinder / grill-with-docs

Goal: clarify the work before building. Use `wayfinder` for foggy, multi-session unknowns; use `grill-with-docs` when the idea can be sharpened against the current codebase and project docs.

2 · Specify

to-spec

Goal: turn the sharpened idea into a concrete spec: behavior, constraints, boundaries, acceptance criteria, and what is explicitly out of scope.

3 · Split

to-tickets

Goal: break the spec into small tracer-bullet tickets with dependencies. Each ticket should be independently implementable and verifiable.

4 · Build

implement

Goal: execute one ticket at a time. `implement` drives the engineering loop, usually pulling in TDD internally for red → green behavior slices.

5 · Check

code review

Goal: review the finished change against both standards and spec before calling it complete.

Why this order matters

It prevents the common LLM failure mode: implementing a plausible solution before the problem is crisp. First reduce ambiguity, then write the spec, then split work, then implement, then review.

Where caveman and Karpathy fit

Caveman compresses communication across the flow. Karpathy rules constrain implementation and review: state assumptions, keep changes surgical, avoid speculative abstractions, verify claims.

Skills are packaged instructions/resources loaded when relevant. Source: Anthropic Agent Skills overview.

Part 5 · MCP model

MCP servers add capabilities through a standard protocol.

Host

OMP / Hermes

Starts the agent session and decides which MCP servers are available.

MCP client

Discovers server capabilities and mediates tool calls.

Model

Chooses tool calls when the prompt and policy allow it.

User

Sees results, approvals, errors, and final output.

Server

Tools

Executable functions: compress, search, query graph, retrieve memory.

Resources

Context data: files, schemas, docs, metadata, state.

Prompts

Reusable templates/workflows exposed to the host.

Policies

Tool approval, filtering, server enablement, and timeouts.

Key distinction: a skill says “how to behave”; an MCP server says “what capability exists”. The harness decides how those capabilities are exposed.

Source: MCP server features overview.

Part 6 · Context MCPs

Context-saving options: LeanCTX used; RTK and Headroom as alternatives.

LeanCTX / `lean-ctx`

Used pathMCP context runtime

Core job: control what the agent reads and how much context it spends.

Capabilities: compressed file reads, signatures/maps/ranges, compact search/tree, shell-output compression, cached re-reads, diff mode, URL reading, MCP tools.

Best fit: local repo work where file exploration and verification would otherwise flood the model.

Presenter line: “LeanCTX is the context budget manager.”

LeanCTX docs

RTK

AlternativeCLI proxy

Core job: reduce token-heavy terminal output from common developer commands.

Capabilities: command interception/proxying, compact output for shell-heavy workflows, Rust single-binary shape in the cited project.

Best fit: teams whose main context waste comes from verbose CLI output rather than file exploration.

Presenter line: “RTK attacks noisy command output.”

RTK site

Headroom

AlternativeMCP compression

Core job: compress large content and let the agent retrieve originals when needed.

Capabilities: `headroom_compress`, `headroom_retrieve`, `headroom_stats`, proxy mode, MCP mode, large logs/files/RAG/tool-output compression.

Best fit: mixed agent/RAG/tool-output environments where compression and reversible retrieval are central.

Presenter line: “Headroom compresses broad content streams.”

Headroom MCP docs

Boundary: LeanCTX is the used context runtime in this workflow. RTK and Headroom are alternatives or complements, not hidden prerequisites.

Part 7 · Long-term memory

Long-term memory: structural graph vs narrative recall.

The useful split: codebase-memory-mcp remembers what the code is; agentmemory remembers what happened and why.

Structural memory
codebase-memory-mcp

Index code

Parse repository files into graph nodes: projects, folders, files, modules, classes, functions, methods, routes, and resources.

Build edges

Capture relationships: imports, defines, calls, handles, HTTP/async links, usages, tests, and file-change affinity.

Ask graph

Use graph queries for callers, callees, architecture, route discovery, impact analysis, hotspots, and dead-code candidates.

Act safely

Use structural answers to choose files and symbols before edits. Treat the graph as rebuildable from code, not as rationale.

Narrative memory
agentmemory

Capture session

Store conversation history, decisions-in-progress, user preferences, debugging discoveries, and why the path changed.

Retrieve context

Recall prior rationale when a future session asks “what did we decide?”, “what did the user prefer?”, or “what broke last time?”

Continue work

Use remembered narrative to avoid rediscovering the same context after restarts, compaction, or a new harness session.

Promote truth

If a decision is accepted and costly to reverse, copy it into durable plain text: project docs, ADRs, or a canonical glossary.

Talk track: “Codebase Memory answers structural questions about the repo. AgentMemory answers narrative questions about the work. Neither replaces durable written decisions.”

Sources: Codebase Memory MCP docs, Codebase Memory MCP GitHub, AgentMemory docs, and AgentMemory GitHub.

Part 8 · Context pipeline

Context pipeline during development

Orient

Map first

Start with directory maps, file summaries, exact ranges, and official resource lists. Avoid whole-repo dumps.

Ground

Trust sources

Use official docs for MCP, OMP, Hermes, LeanCTX, RTK, Headroom, Codebase Memory, and AgentMemory.

Preserve

Write artifacts

Save the deck, handout, resources, notes, mission, and learning records for later teaching sessions.

Verify

Check result

Parse HTML, assert required concepts exist, assert excluded references are absent, then open the deck.

Speaker note: Make clear that context engineering is not just token frugality. It is also source selection, artifact retention, and proof that the output matches the ask.
